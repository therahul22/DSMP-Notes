## 1. Database Architecture Stack
The Database Management System (DBMS) acts as the crucial intermediary layer:
* **Hardware (HDD/SSD):** Physical storage.
* **Operating System:** Manages hardware resources.
* **DBMS:** Software that manages, stores, and retrieves the data (e.g., MySQL).
* **Applications:** The software interface (e.g., a backend API server) requesting data.
* **Users:** End-users interacting with the application frontend.

## 2. Table Terminology (Relational Model)
* **Table:** Relation
* **Row / Record:** Tuple
* **Column / Field:** Attribute
* **Cardinality:** Total number of rows (tuples)
* **Degree:** Total number of columns (attributes)
* **Domain:** Set of acceptable values for a specific attribute

## 3. Database Types & Architecture Choices
Choosing the right database depends heavily on read/write patterns and system design requirements:
* **Relational (SQL):** Row-based (MySQL, PostgreSQL). Best for Online Transaction Processing (OLTP). Ideal when data integrity and strict schema compliance are critical.
* **Columnar:** Column-based (Redshift, BigQuery). Best for Online Analytical Processing (OLAP). Superior for analytics because it reads only relevant columns rather than fetching entire rows.
* **NoSQL (Document):** Unstructured/semi-structured data (MongoDB). Great for flexible schemas and rapid prototyping.
* **Key-Value:** (Redis). Highly optimized for fast caching (e.g., storing a pre-calculated metric to avoid heavy relational queries).
* **Graph:** (Neo4j). Built for querying complex relationships.

## 4. Local Environment: MySQL & Apache XAMPP
* **MySQL Workbench:** The graphical user interface (GUI) used to interact with the database visually.
* **Apache XAMPP:** A local server environment bundle. It packages Apache (web server), MySQL/MariaDB (database server), and PHP/Perl. It provides an immediate, out-of-the-box local testing server environment without needing to configure each component separately.

## 5. Relationships & Cardinality
Cardinality defines the number of instances of one entity associated with another:
* **1:1 (One-to-One):** e.g., Person → Driving License Number.
* **1:N (One-to-Many):** e.g., Student → College Branch, or Restaurant → Menu Items.
* **M:N (Many-to-Many):** e.g., Students ↔ Courses. Requires an intermediate "junction" or "mapping" table (e.g., an `Enrollments` table) to resolve into two 1:N relationships.

## 6. Database Keys (Technical Interview Cheat Sheet)
*Key concepts frequently tested in system design and backend technical rounds.*

* **Super Key:** A single attribute or combination of attributes that uniquely identifies any row within a table. (It can contain extra, unnecessary attributes).
* **Candidate Key:** A *minimal* Super Key. It uniquely identifies a row but has no redundant attributes. A table can have multiple candidate keys.
* **Primary Key (PK):** The specific Candidate Key chosen by the database designer to uniquely identify records. **Must be unique and cannot be NULL.**
* **Alternate Key:** Any Candidate Key that was *not* selected as the Primary Key.
* **Composite Key:** A Primary Key made up of two or more attributes. Used when a single attribute isn't enough to guarantee uniqueness (e.g., `StudentID` + `CourseID` in an Enrollment table).
* **Surrogate Key:** An artificially generated key (usually an auto-incrementing integer or UUID) used when no natural candidate key exists or when natural keys are too bulky.
* **Foreign Key (FK):** An attribute in one table that references the Primary Key of another table. It is the core mechanism for establishing relationships and enforcing referential integrity between tables.
